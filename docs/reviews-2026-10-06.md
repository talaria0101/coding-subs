## Review 2 — OpenCode Go's $60 is a shared pool, not per-model budgets

**Defect.** The 2026-10-02 pass read the vendor grid as independent per-model ceilings and published
its top row as "Muse Spark 1.3 Contributor, II 48.09, $0.0009/M, 53,436 II-points per $/M" — the
whole month spent on one model. `2026-09-20` reached the same reading earlier and published it as
"up to ~$60/mo of list-value usage **across 27 models**", "~6× face".

**The vendor's sentence does not support either reading.** [../2026-10-06/sources/opencode-go.md](../2026-10-06/sources/opencode-go.md),
fetched 2026-10-06, HTTP 200, 39,692 B, `sha256:e62561c5c6fb…`:

> "Each model's monthly limit below determines how its usage counts toward those allowances."

"Counts **toward those allowances**" is compatible with a per-model budget and with a shared pool the
per-model figure bounds. The page does not say which. Both earlier passes resolved an ambiguity in
favour of the reading that flatters the number, without saying they had done so.

**Candidate explanations, enumerated before testing.** Three, and each was testable against a named
artefact:

1. *The docs are right and the ceilings are independent.* Refutable by any report of a model
   blocked while its own usage is near zero.
2. *The ceilings are a shared pool.* Refutable by a report of every model blocking at once with
   total spend well under the pool.
3. *The meter sums per-model percentages rather than dividing dollars by the pool.* Refutable by a
   report whose displayed percentages sum to 100 while its dollars sit far below the pool.

**What settled it.** All three fired, which is the reason this is a range and not a verdict:

## Review 4 — A unit error that reached a headline verdict

**Defect.** A figure of `25.81亿` was read as **25.81 billion** when the stored row said
`monthly_tokens: 2581000000`. 亿 is 10^8, so 25.81亿 **is** 2.581 billion: a 10x error that flipped a
HIT to a PARTIAL only when a second analyst re-derived the arithmetic against the stored row.

**Why it survived, which is the point.** Two independent analysts made the same mis-read from the
same file. Reading a number is not checking one, and care is not the missing ingredient: re-deriving
from a stored row is.

**What this pass does about it.** `unit-scale` compares column pairs that state the same quantity in
different units, and converts rather than copies. `tools/derive-yields.py` prints the whole division
so the arithmetic is inspectable rather than asserted.

**Correct-input demonstration of the arithmetic itself**, at the wall this pass is built on:

```
$ python3 tools/derive-yields.py --ceiling 10 --input 0.10 --output 0.20 --cache 0.002 --mix 100/0/0
ceiling      = $10  (independent per-model ceiling; use --ceiling-basis min --pool P --cap C where a pool exists)
prices       = input $0.1  output $0.2  cache read $0.002 per 1M
mix          = 100% cache read / 0% fresh input / 0% output

  blended $/M = (1*0.002 + 0*0.1 + 0*0.2)
             = 0.002000 $/M

  yield       = $10 / 0.002000 $/M
             = 5,000 M tokens/month = 5.000 B
```

**A figure this pass refused to publish.** The same body of work asserts that "10B of DeepSeek V4.1
Flash at list costs ~$444/month, so a $10→10B route needs a ~44x multiplier". That implies
$0.0444/M. It is not reproducible from any price source this pass can verify: DeepSeek's own
published off-peak tariff [R5] blends to $0.00966/M under the standard mix ($96.60 for 10B, 9.7x),
the peak tariff to $0.01932/M ($193.20 for 10B, 19.3x), and OpenCode Go's DeepSeek rate to the same
$0.00966/M ($96.60, 9.7x) — Go's DeepSeek card *is* DeepSeek's own off-peak tariff to the cent.
**The figure is not carried**, and the wall is published at the rate that
*is* reproducible: 5,000M on the cheapest qualifying price, needing a 2x multiplier over raw credit,
against 9.7x–19.3x on the model a buyer would actually purchase. The conclusion is unchanged and it
does not need the number this pass cannot source.

> **CORRECTION 2026-10-07 — this paragraph's own reference figures were fabricated.** It read
> "$0.01559/M … $155.90 for 10B, **15.6x**" off-peak and "$0.03118/M … $311.80, **31.2x**" at peak.
> **None of $0.01559, $0.155.90, $0.03118, $311.80, 15.6x or 31.2x is derivable from the archived
> page.** The root cause is [Review 7](#review-7--a-fabricated-source-quotation-that-reached-four-published-numbers):
> `references/references.md` R5 misquoted DeepSeek's price table, and these numbers inherited the
> error rather than causing it. The four figures this paragraph published on the strength of a
> fabricated quotation were **15.6x → 9.7x**, **31.2x → 19.3x**, **$155.90 → $96.60** and
> **$311.80 → $193.20**. A paragraph written to demonstrate that one unsourced number would not be
> carried was itself resting on four.

### 5.4 Three bugs in the new checks, found by running them

1. **`unit-scale` was confidently wrong on correct data.** Its first version compared *every* token
   column to every other and reported the correct `tokens_m_advertised=6211` / `tokens_m_measured=2900`

   ceiling and a user meter. The check now compares only column pairs that state one quantity, and
   excludes any column whose name ends `_measured`. Same lesson as the 2026-10-02 pass's

   surfaces a check that is confidently wrong.**
2. **`unit-scale` crashed the gate on a Windows console.** Printing the CJK suffix in a failure
   message raised `UnicodeEncodeError` under cp1252, so the gate died with a traceback instead of
   reporting failures. Failure text is now ASCII.

### 5.5 The grid reproducibility check is platform-dependent, and CI is not the platform that fails

**The original claim in this section was partly wrong and is corrected here.** It read: "The three
CI reproducibility checks pass on Linux. On this host they appear to fail, and the cause is **not** a
content change" and attributed the failure to a Windows `\r\r\n` artefact, while also stating that
the committed CSV, its source page and the artefacts were unmodified.

**The verified diagnosis is narrower than that.** `tools/parse-opencode-go.py` wrote through
`csv.writer(sys.stdout)`, whose default `lineterminator` is `\r\n`.

- On **Linux**, stdout performs no newline translation, so the parser emits `\r\n`. The committed
  `2026-10-02/data/opencode-go-grid.csv` **is** CRLF (79 `\r` bytes), so the output matched and
  `diff -u` passed.
- On **Windows**, text-mode stdout translates each `\n` into a second `\r`, so the same command emits
  `\r\r\n` (158 `\r` bytes) and `diff -u` fails.

Measured on both paths against the committed file:

```
committed         sha256:779312571664b6f7…  6,504 bytes  79 CR
parser, unchanged sha256:91a99bae05f7115f…  6,583 bytes  79 CRLF + 79 bare CR  (\r\r\n)
after collapsing \r\r\n -> \r\n:  byte-identical to the committed file  (True)
parser, fixed     sha256:779312571664b6f7…  6,504 bytes  79 CR
```

**So the CI check on `ubuntu-latest` was green, and the "passes on Linux" half of the original claim
was correct.** A second review asserted the opposite — that the committed file was LF and the
regenerated one CRLF, so the check failed on Linux too. That assertion is wrong: the committed file
is CRLF, not LF. What is genuinely platform-dependent is the *parser*, and that is what was fixed.

**The fix, and which of the two options was chosen.** `tools/parse-opencode-go.py` now pins
`lineterminator="\r\n"` **and** calls `sys.stdout.reconfigure(newline="")`. Pinning the terminator
alone would not help: text-mode translation would still insert the second `\r`. The pair makes the
output byte-identical on either platform, and it matches the committed bytes rather than changing
them — **normalising the parser's output, not the CI comparison**, so CI keeps testing the exact
bytes the repository holds.

Reproducible on any platform, no host-specific paths:

```
$ python3 tools/parse-opencode-go.py 2026-10-02/sources/opencode-go.html > grid.csv
$ diff -u 2026-10-02/data/opencode-go-grid.csv grid.csv
$ echo $?
0
```

**Portability caveat, stated as such.** The other two CI checks —
`parse-aa-models.py` and `extract-token-prices.py` — write through `csv.writer` into an in-memory
`StringIO` with `lineterminator="\n"` and then `Path.write_text`, so they are already deterministic
and were left alone. Only `parse-opencode-go.py` writes CSV to stdout, and only it needed the change.
A future parser that writes to stdout will need the same two lines; the check below is what catches it.

## Review 7 — A fabricated source quotation that reached four published numbers

**This is the most serious defect in the pass, and it is the one that had the most reach.**

**The defect.** `references/references.md` [R5] quoted DeepSeek's published price table as:

> "off-peak $0.007 cache hit / $0.22 input miss / $0.66 output; peak $0.014 / $0.44 / $1.32"

**None of $0.007, $0.22, $0.014 or $0.44 is on the page.** The archived bytes
(`sources/deepseek-pricing.html`, `sha256:210f102275ccf1a6…`, re-fetched 2026-10-07 and
byte-identical) publish, for the `deepseek-flash` column:

```
1M INPUT TOKENS (CACHE HIT)   OFF-PEAK $0.003  $0.022   PEAK $0.006  $0.044
1M INPUT TOKENS (CACHE MISS)  OFF-PEAK $0.15   $0.66    PEAK $0.3    $1.32
1M OUTPUT TOKENS              OFF-PEAK $0.6    $1.98    PEAK $1.2    $3.96
```

The four invented figures are `deepseek-v4-pro` numbers — $0.022 is the V4-Pro off-peak cache hit,
$1.98 the V4-Pro off-peak output, $0.044 the V4-Pro peak cache hit — reassembled into a V4.1-Flash
row. **$1.32 and $0.66 are on the page, which is what made the row look right on inspection.**

**Why this is worse than a wrong price.** A wrong price is a number a reader can check against the
vendor. A *fabricated quotation* is a number that presents itself as having been read from the vendor
and did not. It is indistinguishable from a correct one in the file where it lives, it sits in the
references section whose entire purpose is traceability, and every figure derived from it inherits an
authority it never had.

**Candidate explanations, enumerated before testing.** Three, each refutable against named bytes:

1. *The page changed between the 2026-10-06 fetch and the review.* Refutable by comparing SHA-256s.
2. *The four figures are elsewhere on the page — a second table, a footnote, a JS constant.* Refutable
   by exhaustive extraction of every money token on the page.
3. *They are legitimately on the page and the row is merely mislabelled as off-peak/peak.* Refutable
   by locating which column each figure belongs to.

**What settled it, and how each was excluded.**

1. **Refuted.** Re-fetched 2026-10-07: byte-identical, `sha256:210f102275ccf1a6…`. The page did not
   move, so the error is in what was read out of it, not in what the page says.
2. **Refuted.** Every `$` figure on the page is `$0.003 $0.022 $0.006 $0.044 $0.15 $0.66 $0.3 $1.32
   $0.6 $1.98 $1.2 $3.96` — twelve tokens, and **not one of them is $0.007, $0.22 or $0.014**.
3. **Confirmed as the explanation.** $0.022 and $0.044 are the V4-Pro off-peak and peak cache-hit
   prices; $0.66 and $1.32 are the V4-Pro output prices. The row mixes columns across two models.

**The published numbers it propagated into**, all restated here and in
[../2026-10-06/README.md](../2026-10-06/README.md) §1:

2. **`quoted-money-on-page` is new**: every `$N` figure in a pass's `references/*.md` is checked
